## How the work was staged

I asked for the work in separate steps and reviewed each one before allowing the next:

1. **Grounding, with no code.** "Read through lambda3.py and summarize the actual signatures and behavior of `d0exp_parse_and_typecheck`, `d0exp_evaluate`, `format_type`, `d0val_format`, `d0exp_compile`, and `d0exp_compile_js` ... Flag anywhere the assignment spec's description of these functions doesn't quite match what's actually in the code."
   - Result: `GROUNDING.md` (outside `MySolution/`).
   - The AI ran probes rather than reading the code alone. That surfaced facts that shaped the design:
     - `TypeCheckError` carries no position.
     - `str(LambdaSyntaxError)` appends `(<lambda>, line N)`, so `.msg` must be used.
     - Runtime failures such as `1 / 0` arrive as plain Python exceptions.
     - Recursion fails at about 100 LAMBDA calls (`fact(150)`), and at about 150 nested parentheses in the parser.
     - `print(...)` writes to the real stdout.
     - The `mylib/*.lam` files are declaration files that the single-expression functions cannot see.

2. **Decision on runtime errors.** The AI asked whether type-correct programs that fail at run time should be `-32603` or a new code. I chose a new application code. That became `-32013` with a `kind` field. `RecursionError` maps to it rather than to the timeout code.

3. **Contract before implementation.** "Now let's write RPC.md as specified in Task 1, before any implementation ... I want to review the batch/notification HTTP status logic and the error taxonomy especially closely."
   - Result: `RPC.md` and `rpc.schema.json`.
   - The AI listed the choices it made in section 9 of RPC.md for review. The main ones:
     - Invalid Request always uses `id: null`. This is required by the provided `TEST/test_rpc_api.py`.
     - Valid notifications never get a response, even on error.
     - A primitive `params` is `-32600`, while an array `params` is `-32602`.
     - A batch of 11 or more items is rejected.
   - Example values in RPC.md were generated by running LAMBDA3, not written from memory.

4. **Layout before code.** "Implement the service based on the approved RPC.md ... Show me the file layout before writing all the code."
   - The AI proposed Flask over FastAPI. Its reasons: the handler must own raw-body parsing to produce `-32700`/`-32600`/`204` itself, rather than receive FastAPI's automatic 422 errors; and Flask's test client needs no extra dependency.
   - It proposed separate modules for transport, envelope, methods, deadline runner and adapter, and a worker process per call so a runaway computation can actually be killed.
   - I approved the layout, the Flask choice and installing Flask into a local `.venv`.

5. **Implementation and tests.** The AI wrote `rpc_service/` and `tests/test_rpc_http.py`, then ran both test suites.

6. **Test mapping.** "Map each item to specific test function names before writing them, and show me that mapping first." The tests already existed from step 5, so the AI mapped the existing test names to the ten required behaviors instead of writing new ones. That mapping is in TESTING.md.

7. **Documentation.** README.md, TESTING.md and this file, based on captured command output.

## Problems found during the work

- **The first test runs failed two tests.** The first run passed 46 of 47.
  - A 204 response carried `Content-Type: text/html`, because Flask adds a default content type. The fix removes the header on empty responses.
  - A test assumed a fixed order of the `Allow` header on 405 responses. The order is not fixed, so the test sometimes failed. It was changed to check membership instead.
- **A hand-typed number.** The AI first wrote a hand-typed value for 90! in a test. It was replaced with `math.factorial(90)` before the first run.
- **A blocked check script.** A JSON-checking script for RPC.md ran the deliberately slow `fib(35)` timeout example and blocked. It was stopped and rerun with that example skipped.
